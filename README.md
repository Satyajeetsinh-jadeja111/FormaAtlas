# Forma — modular agent suite

Run with Python 3.10+: `python3 server.py`, then open http://localhost:8000. Install `requirements.txt` first. This is a local functional prototype; do not expose it to the public internet.

## Implemented
- Responsive corporate dashboard, CSS sculptural artwork, Forma wordmark, LinkedIn-only agent library and Starter/Plus/Pro plan concepts.
- Real local signup/login/logout with scrypt password hashes, opaque HttpOnly SameSite=Lax sessions, 24-hour expiration and per-user SQLite workspace storage. No email verification or password reset.
- Private resume and project fact onboarding. Rustico and Outreach Studio start empty; no achievements are invented.
- Equal freelance and hiring positioning in facts-based template drafts, one draft per day in the configured timezone, editable queue, approval and clipboard export. Approval never publishes.
- Daily facts-based template scheduling while the local server runs, with database deduplication by user and local date. The browser may be closed; server downtime is not backfilled beyond the current day. Manual and studio-opening draft preparation are also available. Topic source URLs are stored but never fetched or described as verified news.

## Add an agent
1. Add a stable ID, name, category, description, status and capabilities to `public/agents.js`.
2. Add a view renderer and route in `public/app.js`; use `api('workspace')` for the authenticated user's records. Namespace data by agent ID when adding agents.
3. For external execution, add a server handler that derives identity from the authenticated session. Never accept a user ID supplied by the browser as authorization. Add per-user integration records and encrypt tokens using a server-held key.
4. Declare real setup/lifecycle states. Keep an agent `planned` until execution exists. Require explicit review before external writes.
5. Add cross-account isolation tests and provider failure tests before enabling it.

The public registry is metadata, not an authorization layer. The catalog currently contains only LinkedIn Content; the registry remains reusable. Billing entitlements must be enforced by the server, not registry flags or client controls.

## Service setup still required
- AI: optional Gemini refinement is implemented behind a disabled-by-default server-only provider boundary (`providers.py`). No OpenAI integration or paid resources. No live Gemini request has been made or verified.
- LinkedIn: OAuth connection and approved text publishing are implemented and mock-tested; live access has not been verified. Register a developer app and provision Sign In with LinkedIn using OpenID Connect and Share on LinkedIn. Use `openid profile w_member_social` scopes, exact allowlisted redirects, short-lived single-use state bound to sessions, server-side code exchange and secure token storage. Never request LinkedIn passwords. Token expiry/revocation must return users to reconnect. Sign-in is not identity verification. The callback URI must end in `/api/linkedin/callback`.
- Official LinkedIn references: [API access](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access), [OpenID Connect](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2), [OAuth authorization code flow](https://learn.microsoft.com/en-us/linkedin/shared/authentication/authorization-code-flow).
- Billing: no payment processor or checkout. Plus and Pro are proposed tiers with no price or paid entitlements. Add verified payment webhooks, idempotency and server-side entitlement checks before sales.
- Deployment: not requested and not performed. Public SaaS requires TLS, Secure cookies, hardened origin/host checks, rate limiting, verified email, account recovery, encrypted integration storage, migrations, backups, retention/deletion controls and production monitoring. Local server binds loopback only. SQLite files include personal data; protect the host.
- The running server includes a daily template worker with a unique `(user, local_date)` constraint. Production hosting still needs a supervised always-running worker, monitoring and delivery retries.

## Administrator dashboard and encrypted integrations
Install the dependency with `python3 -m pip install -r requirements.txt`. Create a normal local account first, then stop the server and run `python3 server.py --grant-admin your-account@example.com`. Restart and sign in. The Admin dashboard navigation appears only for accounts granted the role. Roles are checked server-side on every settings/event request; knowing the route does not grant access. There is no first-signup administrator or client-editable role.

Gemini and notification SMTP credentials can now be entered in the Admin dashboard. These are global operator-owned integrations, not personal settings. Saved secrets show only a saved/not-saved status, with blank-to-keep, replacement and removal controls. The encrypted settings record uses Fernet authenticated encryption and a generated `0600` server key in `.forma/server.key` (override with `FORMA_SECRET_KEY_FILE`). Preserve that key securely alongside protected database backups; losing it makes stored settings unreadable. Never commit the key, secrets or database. Protect the local machine; an operator with filesystem access can decrypt settings. Server startup rejects broadly readable key files and key symlinks.

The application Gemini endpoint now reads dashboard settings; legacy environment-only provider configuration is no longer used by the application endpoint. The free-tier confirmation remains explicit. Saving never validates a key by making a live request. Each user’s drafts remain separate, while all authorized users may use the global Gemini configuration within their per-user daily limit. Configure no billing on the Google project; the app cannot verify that status.

SMTP requires host, port, implicit TLS or STARTTLS, sender, destination, username and provider-issued app password/SMTP credential. Do not enter your Forma account password. Both modes validate TLS certificates; plaintext SMTP is disallowed. Emails contain generic action summaries, never resume or draft content. Notifications are enabled only when the administrator selects specific events. Supported completion events are new draft records saved, approval records saved, successful Gemini refinement persisted and confirmed LinkedIn publication. These are storage/action completions, not proof that AI authored a template draft or that a LinkedIn post was published. There is no notification for future agents that have no execution implementation.

Completion records retain delivery states `pending`, `sent`, `failed`, `not_configured` or `disabled`. SMTP failure does not roll back completed work. Delivery currently happens inline with a 10-second connection timeout; no retry queue, background worker or delivery guarantee. A process crash can leave `pending`. Client saves are not a trusted production billing/audit source. Future agents should call `settings.complete` only after their actual successful server-side action and register the event in `settings.EVENTS` and the admin event selector. Keep summaries free of personal content. No live emails or Gemini requests were used during implementation.

## LinkedIn connection, publication and daily operation
LinkedIn Content remains the released built-in agent; YouTube Studio is initially private and requires its own integrations before generation or publication. In Admin, configure your LinkedIn developer client ID, encrypted client secret and **exact registered** redirect URI (local default `http://localhost:8000/api/linkedin/callback`). Enable **Sign In with LinkedIn using OpenID Connect** and **Share on LinkedIn** and ensure `openid profile w_member_social` access. Each user connects their own LinkedIn account through the content studio. Authorization state expires after ten minutes, is single-use and bound to the initiating local session. OAuth callbacks require that same signed-in browser. Member access tokens are encrypted per user and never returned by status endpoints. Expired/revoked tokens require reconnecting; no automatic refresh is assumed. Disconnect removes the local token; revoke the app in LinkedIn to revoke remote authorization.

Publishing is a separate explicit action after saving approval. The server verifies approval against the saved text and the exact text submitted at publication. It sends a public text post through the documented UGC endpoint; only HTTP 201 with a post identifier is recorded as published. No images, other social platforms, auto-posting or bulk outreach. A database claim blocks concurrent and repeated publication attempts. Timeouts/failures are conservatively `unknown` and block retries for that draft: check LinkedIn first. This avoids silently duplicating posts but requires operator investigation. Restarting after a crash may leave `pending`; investigate before retrying. The review status remains separate from publication status.

Enable daily drafting in the profile and set an IANA timezone plus local time. A daemon checks every thirty seconds while `python3 server.py` runs. One facts-based template is queued per local day; it is never automatically approved, posted or sent to Gemini. Invalid timezone/time settings are skipped. If the server starts after the scheduled time, today’s draft is created; missed historical days are not backfilled. Template rotation uses only entered Rustico, Outreach Studio or resume facts and equally invites freelance and full-time work. Optional Gemini refinement remains manual, gated and limited. Live news discovery is still not implemented; provided source URLs are recorded but not fetched or verified.

Live prerequisites still required: your resume/project facts; a LinkedIn app with required products and redirect access; each user's OAuth consent; optional existing free-tier Gemini project/key/model; and SMTP credentials/destination if email is wanted. Do not treat mock tests as verification of app approval, live quota, posting rights or delivery. No live account connection, publication, Gemini request, email or deployment was performed during this work.

Official implementation references: [LinkedIn sharing and UGC post payload](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/share-on-linkedin), [authorization code flow](https://learn.microsoft.com/en-us/linkedin/shared/authentication/authorization-code-flow), [OpenID Connect member profile](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2).

## Images and no-cost branded graphics
Content studio now supports one PNG/JPEG/WebP image per draft (8 MB upload limit), a private preview, a description, replacement and removal. Images are decoded, re-encoded as PNG without original metadata, bounded to 16 million source pixels and 4096px per edge, and stored in SQLite behind authenticated owner checks. Media is excluded from public static serving. Save text edits before changing the image.

The local branded graphic creator builds a 1200px corporate-style card from a supplied headline and brand name using Pillow. It is a deterministic template, not Gemini/AI image generation. Google's current Nano Banana API pricing lists no free tier, including Flash Lite Image; therefore no image-generation API calls or paid fallback are included. See https://ai.google.dev/gemini-api/docs/pricing. Existing Gemini settings continue to control text refinement only.

Attaching/removing/replacing an image resets approval. The approval hash binds saved text, normalized image bytes and description; stale image references cannot approve or publish a different image. Only an explicit publish action registers/uploads the private image to LinkedIn and creates the image post. Upload destinations are limited to HTTPS LinkedIn hosts, with redirects blocked. Image uploads and publications are mock-tested, not live-verified. Existing published posts cannot be retrofitted through this workflow; media controls reject changes after any publication attempt. Text-only posts remain supported, including existing approval records. No automatic publication occurs.

### Automatic daily graphics
New drafts now receive a local branded graphic automatically when the profile has a name and `auto_graphic` is not false. Scheduled drafts and studio-created drafts use the same media helper. Set an optional graphic brand name; otherwise the professional name is used. The topic or selected project supplies a neutral headline. The setting can be disabled in the foundation. Existing drafts/publications are not changed, and adding a generated card always leaves the draft in review. No AI image provider, model download, remote browser automation, or paid API is involved. Tests verify automatic attachment, opt-out, daily deduplication and zero network calls during graphic creation.

## Optional hands-off publication
The user requested hands-off operation after the original review-only flow. Foundation settings now allow 1–10 posts per local day, a start time and 30–720 minute spacing, all within the same local day. Existing users remain in review-only mode until they explicitly enable automatic publication and confirm one-time consent. New scheduled posts are then created with factual template text and a local branded graphic when enabled, approved by the configured automation consent, and submitted to LinkedIn without daily clicks. This is **not** original AI image generation; it makes no Gemini image requests or paid calls. Gemini text refinement remains a separate manual feature.

Existing drafts, manual drafts and already-published posts are never swept into automatic publication. Today's existing drafts count toward the selected daily total. The scheduler emits at most one new draft per user per check and preserves the minimum interval from the previous scheduled creation, avoiding catch-up bursts after downtime. A late restart starts with today's next eligible slot, not missed historical days. The selected number is a maximum; downtime, token expiry, access denial and upload failures can prevent completion. No autonomous retries of uncertain publishing attempts occur.

Pause scheduled work disables future scheduling and automatic publication. A post already submitted may complete. The worker rechecks pause settings before external publication. Per-user slot records expose review, ready, published, paused and failed-or-unknown states in Content studio. Optional administrator notifications can include automatic publication failures. Failed or unknown posts require investigation; LinkedIn access expiry/revocation requires reconnecting. The local server and machine must remain running; this is not an externally hosted always-on service. Automatic text/image publishing was tested only with mocks, not by creating new live posts.

## Automatic Gemini text and recent technology research
Scheduled Gemini writing is now supported in addition to manual refinement. Enable Write scheduled posts with Gemini and its data-transfer consent in the foundation, with admin-held key, free-tier confirmation and an available text model. The owner explicitly requested this workflow in chat; their existing schedule is configured for it. General project/technology posts use only supplied professional facts and commentary; recent-news posts use dated title/summary material from fixed official Google AI, Django and GitHub Engineering RSS feeds. The mixed setting rotates project, technology-perspective and recent-news content. It does not promise every industry or news topic is covered.

Research fetches at most three bounded feeds with eight-second request timeouts, same-host HTTPS redirects, one-megabyte limits, rejected DTD/entities, source-domain checks, dates within the previous seven days and duplicate-source avoidance per workspace. A one-hour in-process cache reduces requests. Gemini receives feed titles/summaries, not complete articles; sources are attributed and their URL retained in the post. This is not Google Search grounding and adds no paid search integration.

AI generation happens after durable slot reservation, outside the SQLite write transaction. Each scheduled draft gets at most one AI attempt. If configuration, provider quota, fresh sources or concurrent edits prevent completion, its slot becomes generation_blocked and the draft stays held; no template fallback is automatically published. Users can see this status, and admins can opt into generation-failure notifications. Up to ten scheduled attempts per user per day are possible under the selected schedule; provider quotas can be lower. There are no paid fallback models, retries or image API requests.

A single live Gemini connection check with generic test text succeeded after the owner saved credentials. The full automated news/image/publishing sequence is mock-tested; no new live posts were created during this change. Existing historical posts remain unchanged. Billing tier cannot be inferred from an API key; the administrator must keep the project without linked billing. Google free-tier data-use terms apply. Model availability and quotas can change.
